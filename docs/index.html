QuantumVault: coins only SHA-256 can unlock

A Bitcoin Cash vault spent with a Winternitz one-time signature, verified on-chain using the loops that shipped in the May 2026 upgrade. No elliptic-curve key ever controls the coins, so Shor's algorithm has nothing to attack. Every spend rotates the vault to a fresh one-time key, which the covenant enforces.

How a spend works

  1. The vault UTXO holds a mutable NFT. Its commitment is the 32-byte root of the current one-time key.
  2. The wallet signs sha256(outpoint ‖ recipient ‖ amount ‖ change ‖ nextRoot) with WOTS.
  3. The covenant rebuilds that message from transaction introspection, so an attacker can't change any field.
  4. It finishes all 67 chains in a loop, folds them into a root, and compares the result to the NFT.
  5. The change must return to the same contract with the NFT updated to nextRoot. Key #0 is now burned forever.

Why it needs BCH 2026

  • Loops (OP_BEGIN/OP_UNTIL): about 600 hash steps fit in a 237-op contract instead of an unrolled script larger than the limit.
  • VM limits (2025): big stack items and a budget priced per byte. The wallet adds a budget pad so the op-cost budget (800 per unlocking byte) covers the hashing.
  • CashTokens: the NFT commitment is the vault's state, and it carries the key chain from one spend to the next.

Threat model

  • Quantum attacker: can break secp256k1, but the vault uses no secp256k1 key. Forging WOTS means inverting SHA-256 (about 2¹²⁸ work even with Grover's algorithm).
  • Mempool front-runner: sees the signature, but the signature covers the outputs and the next key, so any change makes the covenant fail.
  • Key reuse: WOTS is one-time. The covenant burns each key by forcing rotation, and the message binds the exact outpoint.
  • Known limits: this is a proof of concept. Production would add WOTS+ per-chain tweaks against multi-target attacks, an XMSS-style Merkle tree for many keys per root, and a hardware-wallet signer.
